# Monitoring Stack Runbook

## Overview

This runbook documents the setup and troubleshooting of a Docker-based monitoring stack using Prometheus, Node Exporter, Grafana, and Alertmanager. In this task, the stack was installed with Docker Compose, Prometheus was configured to scrape Node Exporter metrics, Grafana was used to visualize those metrics, and Alertmanager was configured to send email notifications through Gmail SMTP.[1][2][3]

The main goal was to bring the full monitoring pipeline into a working state: container orchestration with Docker Compose, host metrics collection with Node Exporter, metrics storage and rule evaluation with Prometheus, visualization in Grafana, and alert delivery through Alertmanager.[4][1][5]

## Architecture

The stack contains four main services:

- **Prometheus**: Scrapes metrics from Node Exporter and evaluates alerting rules.[2][6]
- **Node Exporter**: Exposes host-level machine metrics such as CPU, memory, disk, and filesystem usage.[3][4]
- **Grafana**: Connects to Prometheus as a datasource and displays dashboards such as Node Exporter Full.[7][4]
- **Alertmanager**: Receives firing alerts from Prometheus, groups them, and sends notifications by email.[2][8]

## Task completed

### 1. Install and verify Docker Compose

The environment initially had Docker Compose issues, including a broken `docker-compose` binary that produced a `Bus error (core dumped)`. Docker Compose was then manually installed as the modern Docker CLI plugin, and the working command became `docker compose version`.[9][10]

Commands used:

```bash
uname -m
file /usr/local/bin/docker-compose
mkdir -p ~/.docker/cli-plugins
curl -SL https://github.com/docker/compose/releases/download/v2.29.6/docker-compose-linux-x86_64 -o ~/.docker/cli-plugins/docker-compose
chmod +x ~/.docker/cli-plugins/docker-compose
docker compose version
```

### 2. Start the monitoring stack

After Docker Compose was working, the monitoring stack was started from the project directory containing `docker-compose.yml`. The standard Compose workflow for multi-container applications is `docker compose up -d`, followed by `docker compose ps` to verify container state.[11][1]

Commands used:

```bash
cd ~/monitoring-stack
docker compose up -d
docker compose ps
```

### 3. Fix Docker daemon permission issue

The stack initially failed to start because the current Linux user did not have permission to access `/var/run/docker.sock`. Docker’s Linux post-installation guidance recommends adding the user to the `docker` group so Docker commands can run without `sudo`.[12][13]

Commands used:

```bash
sudo usermod -aG docker $USER
newgrp docker
groups
docker ps
docker compose up -d
```

### 4. Fix Prometheus alert rule file errors

Prometheus initially failed because `alert.rules.yml` contained invalid YAML syntax. Prometheus alert rule files must use valid YAML structure with `groups`, `rules`, valid indentation, and complete PromQL expressions.[6]

Commands used:

```bash
docker compose logs prometheus --tail=100
nano alert.rules.yml
docker compose restart prometheus
docker compose logs prometheus --tail=50
```

A corrected rule file was created for:

- High CPU usage alert.[6][14]
- High memory usage alert.[6][14]
- Low disk space alert.[6][14]
- Node Exporter down alert using the `up` metric.[6][2]

### 5. Verify Grafana dashboard

Grafana was connected to Prometheus and the Node Exporter Full dashboard was imported. This dashboard is a Grafana dashboard that visualizes Node Exporter metrics collected by Prometheus; it is not generated by Node Exporter itself.[7][3]

Validation steps:

- Open Grafana at `http://localhost:3000`.[4]
- Confirm Prometheus datasource is selected.[4]
- Verify CPU, memory, disk, and uptime metrics are visible.[7][4]
- Compare dashboard values with system commands such as `free -h`, `df -h /`, and `uptime` to confirm host-level accuracy.[3][4]

Commands used:

```bash
free -h
df -h /
uptime
```

### 6. Configure Alertmanager email notifications

Alertmanager was configured to send email through Gmail SMTP. The configuration included global SMTP settings, a default route, grouping controls, and an email receiver with `send_resolved: true` so recovery notifications are also delivered.[8][5]

Example configuration elements:

- `smtp_smarthost: 'smtp.gmail.com:587'` for Gmail SMTP.[5]
- `smtp_from` for the sender address.[8]
- `smtp_auth_username` and `smtp_auth_password` for SMTP authentication.[8]
- `group_wait`, `group_interval`, and `repeat_interval` for notification timing.[15][16]
- `send_resolved: true` for recovery emails.[8]

### 7. Restart Alertmanager and send a forced test alert

After replacing the Gmail app password, Alertmanager needed to be restarted to load the updated configuration. A forced test alert can be sent directly to Alertmanager’s HTTP API with `curl`, which is a standard way to validate the notification path without waiting for a real Prometheus alert.[17][18]

Commands used:

```bash
docker compose restart alertmanager
docker compose logs alertmanager --tail=50
curl http://localhost:9093/-/healthy
```

Forced test alert command:

```bash
curl -H "Content-Type: application/json" \
  -d '[{
    "labels": {
      "alertname": "TestEmailAlert",
      "severity": "warning"
    },
    "annotations": {
      "summary": "Test email from Alertmanager",
      "description": "This is a forced test alert to verify email delivery."
    }
  }]' \
  http://localhost:9093/api/v2/alerts
```

This test verifies the Alertmanager-to-email part of the flow. A full end-to-end test can also be done by creating a temporary Prometheus alert rule with `expr: vector(1)`, which always evaluates true and fires after the configured `for` duration.[6][19]

## Challenges faced

### 1. Broken Docker Compose installation

A broken or incorrect `docker-compose` binary caused `Bus error (core dumped)`. This usually happens when the wrong architecture binary is downloaded or the binary is corrupted, and it was resolved by installing the proper Docker Compose plugin binary for the system architecture.[10][20]

### 2. APT package confusion

`apt install docker-compose-plugin` failed because the package was not available in the configured repositories, and there was also an invalid file warning in `/etc/apt/sources.list.d/`. This turned out not to matter because Docker Compose had already been installed manually and was working.[9]

### 3. Docker socket permission denied

The monitoring stack could not start at first because the user lacked permission to connect to the Docker daemon socket. This was fixed by adding the user to the `docker` group and reloading the group membership.[12][13]

### 4. Invalid Prometheus alert rule YAML

Prometheus repeatedly restarted because `alert.rules.yml` contained malformed YAML and broken indentation. Prometheus requires correct YAML syntax and valid alert rule structure for rules to load successfully.[6]

### 5. Understanding Grafana vs Node Exporter responsibilities

There was confusion about whether the dashboard was created by Node Exporter. The correct understanding is that Node Exporter only exposes metrics, Prometheus scrapes them, and Grafana renders them using a dashboard such as Node Exporter Full.[7][3]

### 6. Alertmanager email not arriving

Email delivery required understanding that Alertmanager sends mail only when an alert is actually firing, then again based on `repeat_interval`, and optionally on resolution. Troubleshooting required checking whether Prometheus was producing alerts, whether Alertmanager was receiving them, and whether SMTP settings were valid.[8][2][5]

### 7. Secret handling

The SMTP app password was initially exposed in configuration text during troubleshooting. Once a password is shared in plain text, it should be treated as compromised and replaced immediately with a new Gmail App Password.[5]

## Alert testing procedure

To test each alert one by one, temporarily replace the real PromQL expression with `vector(1)` so the rule always evaluates to true. This is a common way to force an alert in Prometheus and verify the full Prometheus-to-Alertmanager-to-email chain.[6][19]

Example:

```yaml
- alert: TestEmail
  expr: vector(1)
  for: 1m
  labels:
    severity: warning
  annotations:
    summary: "Test email alert"
    description: "Testing Alertmanager email delivery."
```

Then run:

```bash
docker compose restart prometheus
```

Verification flow:

1. Check `http://localhost:9090/alerts` for a firing alert.[6]
2. Check `http://localhost:9093` for the same alert in Alertmanager.[17]
3. Check the destination inbox for the notification.[5]
4. Restore the original expression after testing.[6]

## Key learnings

This task demonstrated how a complete monitoring and alerting stack works as a pipeline rather than as isolated tools. Node Exporter exposes host metrics, Prometheus scrapes and evaluates them, Grafana visualizes them, and Alertmanager handles alert routing and notifications.[2][4][3]

It also highlighted the practical issues commonly faced in real setup work: binary installation problems, Linux permissions, YAML syntax errors, understanding component responsibilities, and email notification troubleshooting. These operational issues are as important as the monitoring configuration itself in getting a working production-like setup.

# Business value

--- A Prometheus + Grafana + Alertmanager setup helps businesses in several practical ways:

--- Less downtime: teams know quickly when CPU, memory, disk, or service availability is unhealthy, which helps reduce outages and their business impact.

--- Faster incident response: alerts and dashboards shorten the time needed to detect and diagnose issues, improving operational response speed.

--- Better decision-making: dashboards provide clear trend visibility, helping teams understand system behavior and capacity needs.
